# Keitaro wrapper

Обёртка над [Keitaro](https://keitaro.io) Admin API:

1. **Создание кампании.** Форма: имя, гео-код страны, оффер (автокомплит). Создаётся кампания
   с доменом, группой и источником из настроек и двумя потоками:
   - поток 1: посетители из указанной страны → редирект на `https://google.com`;
   - поток 2: остальные → выбранный оффер (100%).

   Если поток не создался, кампания откатывается (удаляется).
2. **Редактор потоков по схеме «черновик → публикация»**, как в редакторе заказчика:
   Fetch Streams from KT → правки в локальной БД (добавить, Remove, Bring back, pin) → Push to KT или Cancel.
   Доли офферов всегда в сумме дают 100%.

Стек: Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, httpx, pydantic-settings; фронт на HTML и vanilla JS
(его отдаёт сам FastAPI); тесты на pytest и respx.

---

## Требования

- Python **3.12+** (код использует `datetime.UTC` и синтаксис типов 3.10+). Проверено на Python 3.14;
  на других версиях не запускалось.
- Доступ к Keitaro Admin API: адрес трекера и API-ключ. **Для тестов и для `scripts/fake_tracker.py` трекер
  не нужен.**
- SQLite (входит в Python). Другая БД задаётся через `DATABASE_URL` (не проверялось).
- git, доступ к PyPI для установки зависимостей.

## Установка

```bash
git clone <repo> keitaro-wrapper && cd keitaro-wrapper
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt     # или requirements.txt без тестовых зависимостей
cp .env.example .env                              # и заполнить, см. ниже
```

## Настройка `.env`

`.env` лежит в `.gitignore`, в репозитории только `.env.example`. Секретов в коде нет.

| Переменная | Обязательна | Описание |
|---|---|---|
| `KEITARO_URL` | да | адрес трекера, например `https://tracker.example` (без `/admin_api`) |
| `KEITARO_API_KEY` | да | ключ Admin API Keitaro. Не логируется и не выводится |
| `KEITARO_TIMEOUT` | нет (15) | таймаут чтения ответа, с |
| `KEITARO_CONNECT_TIMEOUT` | нет (5) | таймаут соединения, с |
| `DEFAULT_DOMAIN_ID` | да | домен для новых кампаний (`GET /admin_api/v1/domains`) |
| `DEFAULT_GROUP_ID` | да | группа кампаний (`GET /admin_api/v1/groups?type=campaigns`) |
| `DEFAULT_TRAFFIC_SOURCE_ID` | да | источник трафика (`GET /admin_api/v1/traffic_sources`) |
| `CAMPAIGN_PREFIX` | да | префикс тестовых кампаний вида `test_<фамилия>_`; формат проверяется |
| `FALLBACK_REDIRECT_URL` | нет (`https://google.com`) | куда потоку 1 редиректить гео-трафик |
| `KEITARO_CAMPAIGN_URL_TEMPLATE` | нет | ссылка кнопки View in KT. `{base}` = `KEITARO_URL`, `{id}` = id кампании. По умолчанию `{base}/admin/#!/campaign/{id}/main` (формат проверен в админке). Пустое значение скрывает кнопку |
| `DATABASE_URL` | нет (`sqlite:///./app.db`) | локальная БД |
| `ALLOWED_HOSTS` | нет (`127.0.0.1,localhost`) | разрешённые значения заголовка `Host` (защита от DNS rebinding), через запятую, без порта |

Как узнать ID домена, группы и источника (только чтение):
```bash
source <(grep -E '^KEITARO_(URL|API_KEY)=' .env | sed 's/^/export /')
curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/domains"               | python3 -m json.tool
curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/groups?type=campaigns" | python3 -m json.tool
curl -s -H "Api-Key: $KEITARO_API_KEY" "$KEITARO_URL/admin_api/v1/traffic_sources"       | python3 -m json.tool
```

1. `created_campaigns`, `audit_log`;
2. `streams`, `stream_offers` (черновики редактора);
3. `stream_offers.state`: статус оффера в потоке из Keitaro (`active`, `disabled`, …).

## Запуск

```bash
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```
Если `.env` не заполнен (например, сразу после `cp .env.example .env`), сервер не стартует и пишет,
какие переменные нужно задать, например:
`ConfigError: Configuration error: fill in or fix these variables in .env ...: DEFAULT_DOMAIN_ID, ..., KEITARO_API_KEY`.
Значения в сообщение не попадают. **Тестам и `scripts/fake_tracker.py` `.env` не нужен.**
- http://127.0.0.1:8000/ — создание кампании
- http://127.0.0.1:8000/editor.html — редактор
- http://127.0.0.1:8000/docs — Swagger всех эндпоинтов. Для POST и DELETE нажмите **Authorize**
  и введите `keitaro-wrapper` (это CSRF-заголовок `X-Requested-With`, см. ниже), иначе ответ будет 403 `csrf`.

Авторизации в приложении нет. Запускайте его локально (`127.0.0.1`) и не открывайте в интернет:
у кого есть доступ к приложению, тот действует с ключом Keitaro. Встроенная защита для локального запуска:
- запросы с чужим `Host` отклоняются (`ALLOWED_HOSTS`, защита от DNS rebinding);
- все POST и DELETE к `/api/` требуют заголовок `X-Requested-With: keitaro-wrapper`. Сторонняя страница
  не может его отправить без CORS-разрешения, а CORS приложение не разрешает (защита от CSRF).
  Фронт отправляет этот заголовок сам.


## Как работает редактор

| Кнопка | Что делает | Пишет в Keitaro? |
|---|---|---|
| **Fetch Streams from KT** | загружает потоки и офферы кампании в нашу БД. Поток без офферов показывается просто как поток | нет (только GET) |
| добавить оффер (поиск по названию или ID) | добавляет оффер в черновик и сразу пересчитывает доли (34/33/33 → 4 × 25). Поток становится жёлтым | нет |
| **Remove** | оффер получает 0% и становится серым (removed), остальные пересчитываются | нет |
| **Bring back** | возвращает серый оффер в черновик с пересчётом | нет |
| 📌 (pin) | закрепляет текущую долю: при пересчётах она не меняется. Закрепление — **локальная пометка**: само по себе оно поток жёлтым не делает и в Keitaro не уходит (уходят только доли) | нет |
| **Cancel** | возвращает поток к последнему опубликованному состоянию (снимок с Fetch или Push) | нет |
| **Push to KT** | `PUT streams/{id}` с полным списком не удалённых офферов (с их `state` из Keitaro), затем сверка ответа. Повтор безопасен, см. ниже | **да**, только для кампаний с `CAMPAIGN_PREFIX` |
| **View in KT** | открывает кампанию в админке Keitaro | — |
| **Show All Offers** | список всех офферов трекера (ID, название), только чтение | нет |
| Удалить кампанию | мягкое удаление (`state: deleted`), подтверждение вторым кликом | **да**, только с `CAMPAIGN_PREFIX` |

Правила долей (`app/services/shares.py`):
- удалённые (серые) офферы получают 0% и в Keitaro не отправляются;
- закреплённые активные офферы сохраняют долю;
- остаток `100 − Σ закреплённых` делится поровну между незакреплёнными, целыми числами,
  остаток от деления уходит первым по порядку (пример: 70 на троих → 24/23/23);
- сумма активных **всегда ровно 100**, у каждого активного минимум 1%. Если это невозможно,
  операция отклоняется и ничего не меняется. Так бывает, когда закреплённые доли в сумме больше 100%,
  когда закреплены все офферы, а сумма не 100%, когда незакреплённым не хватает хотя бы 1% на каждого
  и когда убирают последний активный оффер.

Если оффер удалили прямо в Keitaro, после следующего Fetch он остаётся у нас серым (removed), и его
можно вернуть через Bring back.

**Статус оффера в потоке (`state`).** Fetch сохраняет его из Keitaro (`active`, `disabled`, …),
Push отправляет обратно как есть: отключённый в Keitaro оффер наш Push не включит. Изменение `state`
в Keitaro после Fetch считается изменением потока (Push откажет с `changed_in_keitaro`). Bring back
возвращает оффер с последним известным `state`, одинаково с промежуточным Fetch и без него. Новый оффер
добавляется как `active`.

**Безопасный повтор Push.** Перед отправкой Push заново читает поток из Keitaro:
- если там уже лежит черновик (например, прошлый Push сохранился, но ответ потерялся), поток просто
  помечается опубликованным, **повторный PUT не уходит**;
- если PUT не ответил (таймаут), ответил ошибкой 5xx или нечитаемым телом, Push читает Keitaro ещё раз:
  - изменение сохранилось → поток опубликован, в ответе есть пояснение;
  - в Keitaro прежнее состояние → `push_not_applied`, черновик цел, можно нажать Push ещё раз;
  - в Keitaro третье состояние → `push_inconsistent`, черновик цел, нужно разобраться через Cancel и Fetch;
  - поток исчез → `stream_gone`;
  - прочитать не удалось → `push_unknown`, черновик цел, повтор безопасен по первому пункту.
- если в Keitaro один оффер записан дважды, Fetch берёт первую запись (с предупреждением), а Push
  сохраняет его один раз.

### Наши решения (в видео заказчика таких случаев нет)
- **Fetch не перезаписывает поток с неопубликованными изменениями.** Такой поток пропускается
  с предупреждением «Push or Cancel first», чтобы черновик не терялся молча.
- **Push отказывает, если поток изменили в Keitaro после нашего Fetch или Push** (`changed_in_keitaro`).
  Так мы не затираем чужие правки. Нужно сделать Cancel, затем Fetch и повторить изменения.
- **Push проверяет имя кампании живым запросом**, а не по кэшу в БД. Удаление тоже.
- **Доли из Keitaro показываются как есть**, даже если сумма не 100. Такой поток подсвечивается
  красным, и Push запрещён, пока любое изменение не пересчитает доли.
- Fetch и черновик разрешены для любой кампании, Push и удаление — только для `CAMPAIGN_PREFIX`,
  потому что трекер общий.
- Ручного ввода процентов нет: в видео его нет, есть только pin.
- Закрепление не делает поток «неопубликованным» (решение владельца): это локальная подсказка для
  пересчёта. Cancel возвращает и закрепления к состоянию последнего Fetch или Push.
- **Допущение: отключённые (`disabled`) офферы участвуют в делении 100% наравне с активными.**
  В видео и ТЗ нет подсказки, как Keitaro считает долю отключённого оффера, а в тестовом трекере
  таких офферов нет. Поэтому `state` хранится и отправляется как есть, а доли делятся на все
  не удалённые офферы.

## API (примеры)

Все POST и DELETE требуют заголовок `X-Requested-With: keitaro-wrapper` (без него 403 `csrf`).

```bash
B=http://127.0.0.1:8000
H='X-Requested-With: keitaro-wrapper'
curl -s $B/health
curl -s "$B/api/offers?q=offer"                          # автокомплит: по названию или точному ID
curl -s $B/api/geo                                        # коды стран ISO 3166-1
curl -s "$B/api/campaigns?q=test_"                        # кампании из Keitaro + флаг editable

# Часть 1: создать кампанию (префикс добавится сам)
curl -s -X POST $B/api/campaigns -H "$H" -H 'Content-Type: application/json' \
     -d '{"name": "demo_mx", "geo": "MX", "offer_id": 7001}'

# Часть 2: редактор
curl -s -X POST -H "$H" $B/api/campaigns/123/fetch                # Keitaro -> наша БД
curl -s $B/api/campaigns/123/streams                              # из нашей БД
curl -s -X POST -H "$H" $B/api/streams/456/offers -H 'Content-Type: application/json' -d '{"offer_id": 7002}'
curl -s -X POST -H "$H" $B/api/streams/456/offers/7002/pin        # /unpin
curl -s -X POST -H "$H" $B/api/streams/456/offers/7002/remove     # /bring-back
curl -s -X POST -H "$H" $B/api/streams/456/cancel
curl -s -X POST -H "$H" $B/api/streams/456/push                   # единственная запись в Keitaro из редактора
curl -s -X DELETE -H "$H" $B/api/campaigns/123                    # мягкое удаление, только наш префикс
```
Ошибки возвращаются как `{"error": "<code>", "detail": "<текст>", "fields": {...}|null}`:
- 4xx — наши правила (например `duplicate_offer`, `pinned_over_100`, `push_forbidden`);
- 422 + `fields` — Keitaro отклонил данные;
- 400 `bad_host`, 403 `csrf` — защита локального запуска;
- 502 — ошибка, отказ или нечитаемый ответ Keitaro;
- 504 — таймаут.

Адрес трекера и ключ в ошибки и логи не попадают.

- `test_migrations.py` — upgrade, проверка совпадения со схемой моделей, downgrade;
- `test_config.py`, `test_static.py` — настройки, ссылка View in KT, отдача фронта, отсутствие `innerHTML`.

Моки построены на **реальных ответах API**: та же структура полей, но ID, имена, даты и прочие

домены, токены, префикс и фамилию, имена и alias кампаний, офферов, групп и источников, значения
`action_options` и реальные ID. Значения берёт из `.env` и локальных дампов `scripts/out/` и не печатает.
Запускать перед каждым коммитом и ещё раз после первого коммита (тогда проверяется и история).

## Ограничения и что проверено вживую

Проверка шла на общем тестовом трекере с тестовым API-ключом.

- **У тестового ключа нет прав на офферы.** `POST offers` и `GET affiliate_networks` отвечают 403.
  Создать тестовые офферы не получилось.
- **В трекере всего один оффер.** Поэтому вживую редактор проверен **только в сценарии с одним
  оффером и только на чтение**: Fetch реальной кампании, потоки, доля 100%, Σ = 100%, Push для чужой
  кампании запрещён. **Добавление, Remove, Bring back, pin, Cancel и Push с несколькими офферами
  вживую не выполнялись.** Они проверены:
  - мок-тестами (`tests/test_drafts.py`, `tests/test_shares.py`) на фейке, построенном из реальных
    ответов API: та же структура, другие ID;
  - кликами в браузере на `scripts/fake_tracker.py` (в Keitaro не ходит).

  Сам формат `PUT streams/{id}` с офферами проверен вживую на шаге 0 (см. `docs/api-notes.md`).
- **Создание кампании (часть 1) проверено вживую через UI один раз**, 2026-11-19, по разрешению
  владельца трекера: кампания `test_<surname>_ui_live`, гео MX, единственный оффер трекера. В Keitaro
  проверены домен, группа и источник, поток 1 `country accept [MX]` → `https://google.com`, поток 2 —
  этот оффер с долей 100. После проверки кампания сразу удалена (`state: deleted`).
- **Keitaro не проверяет, что сумма долей равна 100%** (он принял share 50 для единственного оффера),
  поэтому сумму гарантирует наш код.
- **Удаление кампаний в Keitaro мягкое:** удалённая кампания отдаёт 404. Повторное удаление уже
  удалённой кампании работает только при наличии нашей локальной записи о ней.
- **Одновременные правки в двух вкладках — известное ограничение** (решение владельца: приложение
  локальное и для одного пользователя). Блокировок и версий у потоков нет. Если одновременно
  отправить правки одного потока из двух вкладок, в нашей БД может остаться сумма ≠ 100 (Push такое
  не отправит, `invalid_shares`) или сброситься флаг «не опубликовано». Решение: перезагрузить
  страницу, сделать Cancel и Fetch. Против чужих правок в Keitaro защита есть (Push сверяет Keitaro
  со снимком), но между этой проверкой и PUT остаётся короткое окно: блокировки в Keitaro API нет.
- **Отключённые офферы** вживую не проверялись (в тестовом трекере их нет), только на моках.
- **Документацию Admin API прочитать не удалось.** В админке она отдаёт 403, публичная страница
  рендерится через JS. Поля сверены по реальным ответам и тестовым запросам (`docs/api-notes.md`).

## Что бы доделал

- **Блокировки потоков:** колонка `version` у `streams` (optimistic locking в SQLAlchemy) и ответ 409
  при параллельной правке; сейчас это известное ограничение.
- **Отключённые офферы и доли** (сейчас допущение, см. «Наши решения»): выяснить у заказчика или в
  Keitaro, как распределяется трафик при `disabled`-оффере, и при необходимости не давать ему долю.
- Проверить вживую сценарии с несколькими офферами, когда появится ключ с правами на офферы
  или второй оффер в трекере.
- Прочитать официальную документацию Admin API (нужна сессия в админке) и сверить с `docs/api-notes.md`.
