# PLAN: обёртка над Keitaro Admin API

Стек: Python 3.12+, FastAPI, SQLAlchemy 2.x, Alembic, httpx, pydantic-settings, pytest + respx.
Фронт: статические HTML + vanilla JS, их отдаёт сам FastAPI.
Репозиторий публичный, поэтому секреты только в `.env` (он в `.gitignore`), в git лежит `.env.example`.

---

## Шаг 0. Разведка API (до написания клиента)

1. Открыть документацию Admin API из админки (`<KEITARO_URL>/admin_api/v1/...`, Swagger/Redoc).
   Выписать нужные эндпоинты и схемы.
2. Сделать реальные **read-only** запросы (`curl` или скрипт `scripts/probe.py`, ключ берётся из `.env`):
   - `GET campaigns`, `GET campaigns/{id}`, `GET campaigns/{id}/streams`
   - `GET offers`, `GET domains`, `GET groups?type=campaign`, `GET traffic_sources`
3. Ответы обезличить (убрать домены, ID, ключи) и сохранить в `tests/fixtures/*.json`.
   На этих фикстурах потом строятся мок-тесты, так что поля будут реальные, а не придуманные.
4. Записать в `docs/api-notes.md`, какие поля и значения нужны, а именно:
   - создание кампании: имя, alias, domain, group, traffic source, тип, состояние;
   - поток: `type`, `schema`, `action_type`, `action_payload`, позиция;
   - фильтр по стране: имя фильтра, `mode`, формат `payload`;
   - офферы потока: структура `offers[]` (`offer_id`, `share`, `state`?);
   - как обновлять офферы потока (PUT стрима целиком или отдельный эндпоинт).
5. Пишущие запросы (POST/PUT/DELETE) проверяются только на кампаниях с префиксом
   `test_<фамилия>_`. После проверки эти кампании удаляются (или архивируются, если удаление недоступно).

Я знаю примерную форму API (`Api-Key` в заголовке, `type`/`action_type`/`filters`/`offers` у стрима),
но использовать её буду только после того, как сверю с документацией и реальными ответами.

## Шаг 1. Клиент Keitaro (`app/keitaro/client.py`)

- `httpx.AsyncClient`: `base_url` и `Api-Key` берутся из настроек, таймауты (connect 5s, read 15s)
  задаются через env.
- Иерархия ошибок: `KeitaroError` → `KeitaroAuthError` (401/403), `KeitaroNotFound` (404),
  `KeitaroValidationError` (400/422, с текстом ошибки от API), `KeitaroUnavailable` (таймаут, сеть, 5xx).
- В логах API-ключ не появляется никогда.
- Методы: `list_offers(query)`, `list_campaigns()`, `get_campaign()`, `get_streams()`,
  `create_campaign()`, `create_stream()`, `update_stream()`, `delete_campaign()`.
- Pydantic-схемы ответов нужны только для тех полей, которые мы используем. Лишние поля игнорируются.
- Тесты: respx-моки на каждый метод и на каждый тип ошибки, плюс таймаут.

## Шаг 2. Модели и миграции

Локальная БД (по умолчанию SQLite, URL задаётся через `DATABASE_URL`):
- `created_campaigns`: какие кампании создали через нашу обёртку
  (`keitaro_id`, `name`, `geo`, `offer_id`, `created_at`, `status`);
- `audit_log`: действия редактора (добавлен или удалён оффер, кампания/поток, доли до и после).

Источник правды по кампаниям и потокам — Keitaro. Локальная БД нужна для истории и аудита.
- Alembic: `alembic init`, начальная миграция; тест, что `upgrade head` → `downgrade base` проходит.

## Шаг 3. Бизнес-логика и эндпоинты

**Сервис создания** (`app/services/creator.py`):
- проверить имя: если префикса `test_<фамилия>_` нет, он добавляется автоматически (префикс задаётся в настройках);
- гео: ISO 3166-1 alpha-2, верхний регистр, по списку кодов;
- создать кампанию с `domain_id`, `group_id`, `traffic_source_id` из настроек;
- поток 1: фильтр `country = GEO`, redirect на `https://google.com`;
- поток 2: оффер `offer_id`, share 100;
- если создание потока упало, откатиться: удалить созданную кампанию и вернуть понятную ошибку.

**Сервис долей** (`app/services/shares.py`, чистые функции, тестируются без сети):
- `rebalance(offers)`: делит 100% поровну, целые числа, остаток уходит первым офферам
  (3 оффера → 34/33/33). Сумма всегда 100;
- добавить оффер: пересчёт поровну;
- удалить оффер: пересчёт поровну. Удалить последний оффер нельзя (ошибка);
- дубликат оффера в потоке не добавляется;
- если Keitaro принимает дробные доли, режим можно поменять (уточню на шаге 0).

**API (`/api/...`):**
| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/offers?q=` | поиск офферов для автокомплита |
| GET | `/api/geo` | список кодов стран |
| POST | `/api/campaigns` | создать кампанию (часть 1) |
| GET | `/api/campaigns` | список кампаний |
| GET | `/api/campaigns/{id}` | кампания + потоки + офферы с долями |
| POST | `/api/streams/{id}/offers` | добавить оффер и пересчитать доли |
| DELETE | `/api/streams/{id}/offers/{offer_id}` | удалить оффер и пересчитать доли |
| GET | `/health` | healthcheck |

Ошибки Keitaro приводятся к JSON вида `{"error": "...", "detail": "..."}` с кодами 400/404/502/504.

## Шаг 4. Фронт (`app/static/`)

- `index.html` — создание: имя (префикс показывается подсказкой), гео (select/datalist),

  После каждого действия данные перечитываются из API, так что на экране то, что реально в Keitaro.

## ПЕРЕДЕЛКА РЕДАКТОРА (2026-11-19, после видео из полного ТЗ)

Шаги 0–4 выполнены. По видео редактор заказчика работает через **локальный черновик и публикацию**,
а у нас правка сразу уходила в Keitaro. Что меняется:

**Остаётся без изменений:** клиент Keitaro, фикстуры и моки, первая миграция, создание кампании
с откатом, `check_secrets.py`, `fake_tracker.py` (его дополняю).

### Новая схема БД (новая миграция Alembic, вторая ревизия)
- `streams`: `keitaro_stream_id` (unique), `campaign_id`, `name`, `position`, `schema`,
  `has_offers`, `dirty` (есть неопубликованные изменения), `published_snapshot` (JSON состояния
  офферов на момент последнего Fetch или Push), `fetched_at`, `pushed_at`.
- `stream_offers`: `stream_id` FK, `offer_id`, `offer_name`, `share`, `pinned`, `removed`,
  `in_keitaro` (есть ли в Keitaro по последней синхронизации), unique (`stream_id`, `offer_id`).
- `created_campaigns` и `audit_log` остаются. В `audit_log` добавляются действия fetch, push, cancel,
  pin, remove, bring_back и campaign_deleted.

### Доли с pin (`app/services/shares.py`, чистые функции)
`rebalance(offers)`: удалённые получают 0. Закреплённые активные сохраняют свою долю. Остаток
`100 − Σ закреплённых` делится поровну между незакреплёнными активными, целыми числами, остаток
от деления уходит первым. Сумма активных всегда ровно 100. Операция **отклоняется** с понятной
ошибкой и база не меняется, если:
- сумма закреплённых больше 100;
- все активные закреплены, а их сумма не равна 100;
- незакреплённым достаётся меньше 1% каждому (например, закреплено 99%, а незакреплённых двое);
- удаляется последний активный оффер.

Pin закрепляет текущее значение доли, ручного ввода процентов нет, как в видео.

### Поведение
1. **Fetch Streams from KT** (любая кампания, только чтение из Keitaro) переносит потоки
   и офферы в базу и обновляет снимок. Поток без офферов просто показывается как поток.
   Оффер, который пропал из Keitaro, становится `removed`, то есть серым (п. 6). Закрепления сохраняются.
   *Поток с неопубликованными изменениями при Fetch не перезаписывается*, в ответе есть предупреждение.
2. **Добавить оффер** (по ID, поиск через `/api/offers`) меняет только базу и сразу пересчитывает
   доли (3×33 → 4×25). Поток становится `dirty` и подсвечивается жёлтым.
3. **Remove** даёт офферу долю 0 и снимает pin, остальные доли пересчитываются, поток становится `dirty`.
   **Bring back** делает обратное с пересчётом.
4. **Cancel** восстанавливает офферы потока из `published_snapshot`: добавленные удаляются, доли,
   закрепления и флаги removed возвращаются. Поток перестаёт быть `dirty`.
5. **Push to KT** разрешён только для кампаний с нашим префиксом. Отправляет
   `PUT streams/{id} {"offers": [...]}` с полным списком активных офферов (removed не отправляются)
   и сверяет ответ: те же offer_id, те же доли, сумма 100. Потом обновляет снимок и `in_keitaro`
   и снимает `dirty`. Если сверка не сошлась, поток остаётся `dirty`, и об этом выводится ошибка.
6. **Удаление кампании** (новое): `DELETE /api/campaigns/{id}`, только для нашего префикса,
   мягкое удаление в Keitaro. Если Keitaro ответил 404, кампания считается уже удалённой.
   Обновляет `created_campaigns.status = deleted`. Через этот эндпоинт приведу в порядок запись
   о 900003 (это DELETE на уже удалённую кампанию, перед отправкой напишу, что отправляю).

### Эндпоинты (старые add/remove с мгновенным PUT убираются)
`POST /api/campaigns/{id}/fetch` · `GET /api/campaigns/{id}/streams` (из базы) ·
`POST /api/streams/{sid}/offers` · `POST /api/streams/{sid}/offers/{oid}/remove` ·
`.../bring-back` · `.../pin` · `.../unpin` · `POST /api/streams/{sid}/cancel` ·
`POST /api/streams/{sid}/push` · `DELETE /api/campaigns/{id}` · `GET /api/campaigns/{id}/kt-link`.

### Фронт (редактор)
Кнопки: Fetch Streams from KT, View in KT, Show All Offers, Push to KT, Cancel, Remove,
Bring back и значок pin у каждой доли. Неопубликованный поток подсвечивается жёлтым,
удалённые офферы серые. Колонок Stats и Trends нет.

### Тесты
- Чистые тесты долей с pin: сумма закреплённых больше 100, все закреплены, остаток не делится нацело,
  закреплено 99% при двух незакреплённых, пример из видео (pin 25 → bring back → закреплённая доля
  остаётся 25).
- Мок-тесты всех сценариев 1–6 на фикстурах.
- Миграция `upgrade`/`downgrade` через обе ревизии.
- Проверка в браузере на `fake_tracker`, в том числе «оффер удалён прямо в KT → Fetch → серый».
